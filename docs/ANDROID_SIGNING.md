# Подпись Android-сборки и Play Protect

## Почему это важно

Play Protect (Google Play Защита) блокирует установку приложения предупреждением
«Небезопасное приложение заблокировано» в двух основных случаях:

1. **APK подписан отладочным ключом.** Стандартный debug-ключ Android
   (`CN=Android Debug`) одинаков у всех разработчиков мира и считается
   недоверенным. Именно это происходит с `flutter build apk`, если не настроена
   релизная подпись.
2. **Приложение неизвестно Google и ставится из неизвестного источника.** Даже
   корректно подписанный APK, скачанный «сбоку», первое время может показывать
   предупреждение — Play Protect не видел этой подписи раньше.

Первый случай закрывается собственным ключом подписи — это сделано в
`android/app/build.gradle.kts` и описано ниже. Второй закрывается раздачей через
Play Console (внутреннее тестирование) — тоже описано ниже.

Честно: **никакой «сертификат», который просто кладётся в репозиторий, не даёт
гарантированного пропуска Play Protect.** Гарантию даёт только распространение
через Google Play. Всё остальное — снижение вероятности предупреждения.

## Шаг 1. Создать ключ подписи

Локально, на своей машине (не в облаке, не в CI):

```bash
./tool/make_keystore.sh
```

Скрипт создаёт `~/.signalai/upload-keystore.jks` (RSA 4096, срок 10000 дней),
пишет `android/key.properties` для локальных сборок и печатает отпечатки
SHA-1/SHA-256.

**Сделайте офлайн-бэкап `.jks` и паролей.** Потеря ключа означает, что обновить
уже установленное приложение будет невозможно — только удалить и поставить
заново.

Файлы `android/key.properties`, `*.jks`, `*.keystore`, `*.base64` уже в
`.gitignore`. В git они попасть не должны.

## Шаг 2. Локальная сборка

```bash
flutter build apk --release \
  --dart-define=SIGNALAI_MODE=thin \
  --dart-define=SIGNALAI_API_BASE_URL=https://ваш-гейтвей
```

Проверить, что подпись не отладочная:

```bash
$ANDROID_HOME/build-tools/35.0.0/apksigner verify --print-certs \
  build/app/outputs/flutter-apk/app-release.apk
```

В выводе `Signer #1 certificate DN` должен быть `CN=SignalAI`, а не
`CN=Android Debug`. Если Gradle не нашёл `android/key.properties`, он напечатает
предупреждение и подпишет отладочным ключом — такую сборку на телефон не ставьте.

## Шаг 3. Секреты в GitHub

`Settings → Secrets and variables → Actions`:

| Секрет | Значение |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | содержимое `upload-keystore.jks.base64` |
| `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
| `ANDROID_KEY_PASSWORD` | пароль ключа (тот же) |
| `ANDROID_KEY_ALIAS` | `signalai-upload` |
| `SIGNALAI_API_BASE_URL` | `https://…` — адрес мобильного гейтвея |

Для личного sideload предпочтительно завести отдельную постоянную идентичность:

| Секрет | Значение |
|---|---|
| `SIDELOAD_KEYSTORE_BASE64` | тот же формат base64, но для sideload-key |
| `SIDELOAD_KEYSTORE_PASSWORD` | пароль sideload-keystore |
| `SIDELOAD_KEY_PASSWORD` | пароль ключа |
| `SIDELOAD_KEY_ALIAS` | alias ключа |

`Android sideload APK` сначала ищет полный комплект `SIDELOAD_*`, затем для
совместимости — полный комплект `ANDROID_*`. Если нет ни одного полного
комплекта, сборка завершается ошибкой. GitHub Actions cache не используется как
источник ключа: cache может быть удалён, после чего Android уже не установит
обновление поверх предыдущей версии.

Какой ключ выбрать, зависит от уже установленной сборки. Чтобы обновление
встало без удаления данных, новый APK должен иметь тот же SHA-256 сертификата,
который показан в metadata предыдущей поставки.

После добавления удалите локальный файл с base64:

```bash
shred -u upload-keystore.jks.base64
```

## Шаг 4. Сборка в CI

Workflow `.github/workflows/android-release.yml` запускается по тегу или вручную:

```bash
git tag v1.0.0 && git push origin v1.0.0
```

Он собирает `.aab` (для Play Console) и `.apk` (для установки на своё
устройство), проверяет подпись через `apksigner` и падает, если подпись
отладочная. Артефакты — во вкладке Actions → нужный run → Artifacts.

Запустить вручную: Actions → «Android release» → Run workflow.

Текущий персональный канал — отдельный workflow **Android sideload APK**. Он
принимает обязательный `source_ref`, сначала прогоняет общий Quality gate и
публикует как стабильный файл, так и traceable-файл с ref/SHA. Ни release, ни
sideload не должны получать `SIGNALAI_DEVICE_TOKEN` через `--dart-define`:
скомпилированная строка извлекается из APK и не является секретом.

## Шаг 5. Чтобы Play Protect молчал

По возрастанию надёжности:

**А. Просто поставить подписанный APK.** Android спросит разрешение на установку
из неизвестного источника, Play Protect может показать разовое предупреждение
(«Отправить на проверку» / «Всё равно установить»). Дальше приложение работает.

**Б. Внутреннее тестирование Google Play (рекомендуется).** Аккаунт разработчика
стоит $25 единоразово. Загружаете `.aab` в трек «Внутреннее тестирование»,
добавляете свой аккаунт в тестировщики и ставите приложение по ссылке из Play.
Play Protect не ругается вообще: приложение пришло из Play и проверено. Плюсом
получаете автообновления. Для приложения «только для себя» публикация в открытый
доступ не нужна — внутренний трек не виден посторонним.

**В. Play App Signing.** При первой загрузке в Play Console включается по
умолчанию: Google хранит ключ подписи приложения, ваш ключ становится ключом
загрузки. Это дополнительно защищает от потери ключа.

Ещё две мелочи, которые уменьшают подозрительность сборки и уже сделаны:

* `applicationId` — собственный (`ru.signalai.app`), не дефолтный `com.example.*`;
* релиз собирается с R8 и без отладочных флагов, `usesCleartextTraffic=false`,
  `allowBackup=false`.

## Если Play Protect всё же ругается

1. Убедитесь, что ставите именно release-APK (проверка `apksigner` выше).
2. В Play Protect нажмите «Отправить приложение на проверку» — после проверки
   предупреждение обычно исчезает.
3. Надёжное решение — вариант Б: раздача через внутреннее тестирование Play.

Не отключайте Play Protect целиком: это снимает защиту со всего устройства, на
котором вы подтверждаете сделки.
