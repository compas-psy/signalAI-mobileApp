# Процесс разработки SignalAI

SignalAI выпускается как персональный продукт: один владелец, один серверный
источник истины и тонкий Android-клиент. Это упрощает продукт, но не отменяет
дисциплину поставки — приложение подтверждает и сопровождает сделки.

## Роли и границы

| Роль | Отвечает | Не меняет одновременно |
|---|---|---|
| Product owner / CPO | сценарий, риск, критерии приёмки, решение о live | код и пороги без зафиксированного решения |
| Quant / research | торговые правила, признаки, backtest, качество идеи | UI, исполнение и CI |
| Backend | OpenAPI, БД, миграции, расчёт, paper lifecycle, audit | мобильную копию той же бизнес-логики |
| Mobile | отображение, ввод решения, биометрия, ручная привязка device token и Keystore, push | server risk, sizing, signal generation |
| QA / DevOps | contract/E2E-проверки, workflows, подпись, provenance, sideload | продуктовую логику |
| Integrator / CTO | декомпозиция, владение файлами, merge, решение конфликтов | параллельную реализацию вместо назначенного владельца |

Перед началом итерации интегратор записывает владельца каждого каталога и
контракта. У одного файла в один момент времени только один автор. Если задача
пересекает границу, следующий участник начинает после передачи контракта или
работает в другом файле; два агента не исправляют один и тот же код параллельно.

## Branch и PR flow

1. Для вертикального среза создаётся короткоживущая ветка от одной назначенной
   integration-ветки: `feat/...`, `fix/...` или `ops/...`.
2. В задаче до кода фиксируются API, состояния, ошибки и DoD. Для торгового
   решения отдельно фиксируются fail-closed поведение и `paper_only`.
3. Изменения идут небольшими PR. Один PR — один связный результат, а не набор
   несвязанных правок «заодно».
4. `Quality gate` обязателен для PR. Прямой push не является способом обойти
   красную проверку.
5. После приёмки PR вливается в единственную delivery-ветку. Долгоживущие
   «release» и «UX» ветки с разной логикой запрещены.

Историческая причина правила: на 6 августа 2026 ветка по умолчанию
`claude/release-y40hk5` и активная `claude/ux-prototype-dark-theme-sv0euq`
разошлись от общего предка на 23 и 102 коммита соответственно. APK и VPS могли
получать разные реализации. Поэтому sideload и оба VPS-workflow теперь
manual-only, требуют явный `source_ref`, один раз разрешают его в commit SHA и
передают один и тот же SHA в QA, checkout и удалённый `git fetch`. Жёстких ссылок
на старые release/UX-ветки в поставке больше нет.

## Порядок одного вертикального среза

1. **Server contract.** Backend фиксирует request/response envelope, статусы,
   идемпотентность, `404/409`, миграцию и contract-тесты.
2. **Server behavior.** Реализуется расчёт или lifecycle. Все решения и журнал
   живут на сервере; телефон не содержит запасной расчёт того же результата.
3. **Mobile.** Клиент подключается к принятому контракту, показывает loading,
   empty, stale и error состояния и не превращает наблюдение в подтверждённый
   сигнал.
4. **QA.** На точном ref запускается `Quality gate`: secret scan, импорт API,
   Alembic, pytest на PostgreSQL, `flutter analyze` и `flutter test`.
5. **Sideload.** После зелёного gate вручную собирается подписанный APK того же
   ref. Публикация обновляет стабильный канал и сохраняет SHA/подпись/хеш APK.

Для первой поставки решения по идее контрактом считаются:

- `POST /api/v1/ideas/{id}/approve-paper`;
- `POST /api/v1/ideas/{id}/reject`;
- envelope
  `{idea_id, decision, idea_status, paper_only:true, idempotent_replay, decided_at, reason?, comment, trade?}`;
- approve создаёт только серверную paper-сделку, reject пишет append-only
  решение, повтор запроса идемпотентен, `404/409` закрывают действие.

## Definition of Done

- API и мобильная модель совпадают по именам, nullable-полям и состояниям;
- server-зависимости устанавливаются только через `uv sync --frozen` из
  `server/uv.lock`; CI проверяет актуальность lock и запрещает его изменение;
- миграционный граф имеет один head, `upgrade head` и `alembic check` проходят;
- весь server pytest проходит на PostgreSQL, а не на SQLite;
- `flutter analyze` и `flutter test` проходят на закреплённой версии SDK;
- нет секретов в git, логах и `--dart-define`; bearer-token не лежит в APK;
- production deploy падает без явного `SIGNALAI_DEVICE_TOKEN`, не выводит
  его и не выводит из SSH-ключа;
- серверная операция идемпотентна, audit append-only, live не включается
  обходом `paper_only`;
- ошибки сети, пустые данные и отсутствующие свечи видны пользователю и не
  приводят к вылету;
- ручная проверка на устройстве включает холодный старт, обновление поверх
  предыдущего APK без потери данных, график, approve/reject и повтор запроса;
- sideload metadata содержит точные source ref/SHA, SHA-256 APK, отпечаток
  сертификата и ссылку на workflow run;
- Product owner принял сценарий на paper-контуре. Live — отдельное решение.

## Как выпускать sideload

1. Открыть Actions → **Android sideload APK** → **Run workflow**.
2. В `source_ref` указать принятую ветку, тег или полный commit SHA. Выбор ветки
   в верхней части формы определяет версию самого workflow, но не заменяет этот
   обязательный параметр.
3. Для рабочей сборки оставить `mode=thin`; `demo` предназначен только для UI.
   Legacy-режим `local` в персональной поставке недоступен.
4. Workflow сам вызывает `Quality gate` на том же ref и прекращает сборку при
   любой ошибке или отсутствии постоянного signing secret.
5. Установить стабильный `signalai-sideload.apk`. Рядом публикуются APK с ref и
   SHA в имени и `signalai-sideload.json` с provenance.

Обычный push APK не выпускает. Альтернатива кнопке — специальный тег
`sideload-*`; в этом случае источником является commit самого тега.

`thin` означает одну границу ответственности: сервер считает идеи, ведёт
paper-сделки и фоновые задачи; телефон показывает и передаёт подтверждённое
владельцем решение. Локальный скринер в этом режиме не запускается.

Первая привязка на этом этапе не автоматизирована. Владелец сам создаёт и хранит
`SIGNALAI_DEVICE_TOKEN`, добавляет его в repository Secrets, deploy записывает
тот же token на VPS, а владелец один раз вводит его в приложении. После ввода
он хранится в Android Keystore. Pairing endpoint — отдельный следующий
контракт, не часть текущего DoD.

## Как развёртывать сервер

- **Deploy release to VPS** — обычное обновление работающего сервера. Запуск
  только вручную, с обязательным `source_ref`; полный Quality gate проходит до
  доступа к VPS.
- **Развернуть сервер на VPS** — bootstrap и эксплуатационная диагностика
  (`health`, `logs`, `tls`, `caddy`). `bootstrap` и legacy-действие `update`
  также проходят Quality gate.
- Оба workflow используют общую concurrency-группу: два изменения одного VPS
  не выполняются одновременно и начавшийся деплой не отменяется посередине.
- В summary и логах всегда показывается разрешённый SHA. Удалённый сервер
  проверяет, что `FETCH_HEAD` совпадает с ним, до миграций и перезапуска.
- Для `bootstrap`/`update` обязателен repository secret `SIGNALAI_DEVICE_TOKEN`.
  Workflow заканчивается до SSH, если его нет, и нигде не печатает значение.
