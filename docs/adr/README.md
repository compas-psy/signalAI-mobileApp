# Architecture Decision Records

ADR фиксируют существенные решения SignalAI, которые влияют на деньги, безопасность, несколько подсистем или задают долгосрочный технический стандарт.

## Когда нужен ADR

Создавать ADR, если решение:

- трудно или дорого отменить;
- меняет границу ответственности между mobile/server/broker;
- влияет на secrets, auth, signing, network trust или live trading;
- меняет risk engine, execution model, order lifecycle или promotion gates;
- вводит новую инфраструктурную/архитектурную зависимость;
- меняет стандарт, который должны соблюдать будущие агенты.

Не нужен ADR для локального bugfix, текста, небольшого UI-изменения или реализации уже принятого решения.

## Нумерация и статус

Файлы: `NNNN-kebab-case-title.md`.

Статусы:

- `proposed` — обсуждается;
- `accepted` — действует;
- `superseded` — заменён новым ADR;
- `rejected` — рассмотрен и отклонён.

Accepted ADR нельзя отменять скрытым рефакторингом. Новое решение создаёт новый ADR и явно указывает `Supersedes: ADR-NNNN`.

## Минимальная структура

1. Контекст и проблема.
2. Decision drivers / ограничения.
3. Рассмотренные варианты.
4. Решение.
5. Последствия и риски.
6. Проверка/acceptance criteria.
7. Условия пересмотра.

Использовать `0000-template.md`.
